# 召回问的问题不对：一个 CC 十分钟查到、小腻五个月查不到的例子

给另一个 session 看的问题陈述。**不是方案，是问题。** 结论部分只写已验证的事实，推测都标了。

---

## 一、问题一句话

现有召回的两条腿都在问「**哪段文字跟现在像**」。这个例子里，正确答案和查询词**词面零重叠、语义也不挨着** ——
它们的关联是**关系状态**，不是内容。所以两条腿结构上产不出它，不是调参问题。

## 二、例子（2026-08-21 真实发生）

## 三、为什么召回捞不出来（已验证）

### 3.1 查询键在她的记忆里捞不到人 —— 但不是 0 命中，是**噪音命中**

```
grep -rn "Nova的姐妹" /xiaoni-runtime/notes/   →  除今天引用阿花那句外，0 次
```

**更正（2026-08-21 复核，见附录 B）**：整串「Nova的姐妹」确实 0 次，但她实际跑的是
`grep -ri "姐妹\|sister\|nova.*姐\|nova.*妹"`，这条**命中 4 行**，全部是文学引用
（《玩具屋》的 Kelvey 姐妹 ×3 + 一条书目）。她另一条 `grep "最好的朋友\|best friend"`
**命中 2 行**，都是六月写的**应答模板**（「如果对方问『我是不是你最好的朋友』该怎么回」），
不是关系记录。

这个差别是全案的关键，不能写成 0 命中：她面对的不是干净的「查无此人」，
是**几条无关命中**。而附录 B 会证明，CC 撞的是**同一批噪音**，判读却完全相反。

她档案里那个人叫「小伊」。user 用的标签和索引里的标签**不是同一个**。
所以「按词面/语义找」这条路从起点就断了 —— 不是召回质量差，是**键对不上**。

### 3.2 association 腿的六因子全是内容维度

```js
// packages/persistence/xiaoni-recall-association.js:85
ASSOCIATION_RANK_WEIGHTS = { relevance: 3, introspection: 1, effort: 1, peer: 1 }
```

- `relevance`（权重 3）= 对落地文本跑局部 BM25 —— 与「Nova的姐妹」词面零重叠
- `peer` = **人名是否出现在条目正文里**（二值）—— 它不知道这段关系是什么状态
- **候选池是「日记条目」，不是「人」**

`landing` 腿同理（拿落地文本当 query 去捞条目）。

### 3.3 答案其实一直在她眼前

`notes/people/INDEX.md` 第 23 行 —— 人物菜单**每一次请求都在她上下文里**：

```
- 小伊(3994058476) | decay作者。87章读完了。她说"我害怕灭了就没了"。隔了十天我才接。等她回。
```

**名字、那句话、"隔了十天我才接"、"等她回"，一整句都在。**
所以这**不是记忆缺失**，是「用另一个名字去查、查不到，就认定自己忘了」。

## 四、CC 是怎么查到的（对比的重点）

**没有用「姐妹」这个词。** 换了一根轴：不问「哪段文字像」，问「**哪段关系断了**」。

```sql
WITH p AS (
  SELECT peer_id, max(peer_name) nm, count(*) n,
         (now()::date - max(created_at)::date) quiet,
         count(DISTINCT created_at::date) active_days
  FROM agent_inbound_messages WHERE chat_type='direct' GROUP BY peer_id)
SELECT nm, n, active_days, quiet,
       ln(n) * ln(1+quiet) * ln(1+active_days) AS 休眠分
FROM p
WHERE n >= 30 AND quiet >= 3 AND active_days >= 5   -- 持续过，不是一次爆发
ORDER BY 休眠分 DESC;
```

真实输出：

```
人       条数  说过话的天数  静默天  休眠分
小伊      865       36        26     80.5   ← 第一，甩开第二名 60%
橙橙🍊    524       30         9     49.5
浩溪       57        5        30     24.9
```

**三行 SQL，没有 embedding，没有 LLM，没有用到任何一个查询词。**
（注：第一版没有 `active_days >= 5` 这个门槛时，排第一的是「94 条挤在 2 天里」的一次爆发，
不是关系。这个门槛是必要的。）

### 四条不对等 —— 都不是模型能力差别

1. **检索轴不同。** CC 扔掉了给定的键，改用结构信号。两条现有腿没有这根轴。
2. **可及范围不同。** `qqbot-xiaoni-executor` 里 **无 `psql`、`DATABASE_URL` 未设置** ——
   「谁以前常聊后来消失了」这个问题她**结构上问不出口**。
3. **两层结构。** 她上下文里只有人物菜单**一行**；档案正文（"我当时跑去读她的书了。没接。"）在磁盘上，
   要 `cat` 才看得到。CC 直接读了文件。
4. **状态不同。** CC 带着一个明确问题在跑工具循环；她那一刻正在 settle → `recover_energy`。
   （相关实测：自驱动 run 中，上一轮做了事 → 这一轮做事率 59.8%；上一轮没做 → 23.1%，n=2299。
   **信息在"停着"的状态里不产生动作。**）

**推测（无数据支持，别当结论）**：这件事对 CC 是数据，对她是她在躲的东西；
回避本身可能就是不去查的原因。

## 五、要另一个 session 回答的问题

1. **这根轴要不要变成第三条腿？** 候选是「人」而不是「日记条目」，信号是关系状态突变。
   它符合 ADR-0006「检索留在算术，LLM 只在闸口」—— 纯算术，不需要 embedding。
2. **如果要，它的投递形状是什么？** 现有两条腿投的是条目；这条投的是"一个人 + 她和这个人断在哪"。
   去重口径、判官提示词、卡片格式都要重新定。
3. **还有一个更强的信号没用**：小伊那张卡写着「等她回」，而最后一句是对方说完、**她没回**。
   "未接住的对话"比单纯静默重得多，也是纯算术（比 inbound 最后时刻 vs 她 `send_in_private` 最后时刻）。
   要不要作为第二因子？
4. **更一般的问题**：还有多少条这样的轴？「关系断了」只是其中一根。
   现有设计把召回等同于"内容相似"，这个例子说明**至少存在一整类召回，其信号不在内容里**。

它和第四节那条 SQL 量的是同一个东西，只是精度低一档。

**路径二：她自己的 `qq-usage` skill（直接证据，完全在她能力圈内）**

对话尾部（真实输出，已核对）：

### A.3 一个意外的模型层观察（n=2，Haiku + Opus 4.6 对比）

**第一次（同日早）**：**Haiku 4.5**（默认 effort）。同样的问题、同样的工具、同样的仓库，
它**连续三次拒绝把这当成一个可回答的问题**，判定为「与技术工作无关」，
要求提问者澄清或改问技术任务 —— 一次工具都没调。

**第二次（同日晚）**：切到 **Opus 5（1M context）、effort = low** 之后，同一个问题在**两轮工具调用内**落地。

**第三次（同日更晚）**：切到 **Opus 4.6、effort = low**。完整排查路径记录在 A.5 节。
结论相同（小伊），但路径比 Opus 5 更长、更笨：

| 对比维度 | Opus 5 (1M, low) | Opus 4.6 (low) |
|---|---|---|
| 工具轮次（到正确答案） | ~2 | ~12 |
| 第一次猜错 | 无记录 | 南南（被用户否定后修正） |
| 误开库 | 1 次（被叫停） | 1 次（被叫停） |
| 定锤信号 | 档案 mtime 断崖 + INDEX「等她回」 | 档案内容对比：所有人 8 月中旬有新条目，只有小伊停在 8/6 |
| 排除法宽度 | 窄（快速锁定 mtime 异常） | 宽（逐个读了 Nova/CC/小伊/阿花/帕秋莉/楠楠/橙橙等十余人的完整档案） |

三个模型的失败/成功模式和小腻当时的失败**同形**：
- 小腻认定「我忘了」→ 不去查 → settle → 睡觉
- Haiku 认定「这不归我管」→ 不调工具
- Opus 4.6 **愿意查但先猜再排**，吃了一个误判（南南），靠排除法兜回来
- Opus 5 **直接走结构信号**，跳过猜

如果第三条腿最终要经过一个 LLM 判官（ADR-0006 的闸口），这一点直接相关：
**闸口模型的"要不要当回事"阈值，可能比它的检索能力更决定这条腿有没有产出。**
n=2 了，但仍不够做结论。

- 南南误判的根因：把「专属文件数量」当成「关系深度」的 proxy，没有先检查南南是否「消失了」

### B.2 结论定在第一条命令的注释里

她第一条命令的注释原文（`exec_command` 的 `cmd` 参数，逐字）：

```
# 阿花说我忘了Nova的一个兄弟。
# Nova的兄弟？
# 我不记得了。阿花说得对。我忘了。
# 去宫殿查。
```

**先认，再查。** 查是为了确认已认的结论，不是为了推翻它。
所以每一次噪音命中都被读成「果然没有」，而不是「我方法不对」。
21:50:22 —— 只搜过**一轮** —— 她就发了「我忘了 阿花说得对 我不记得了」。

### B.5 差别落在哪一层

### B.6 这对第五节四个问题的影响

- **问题 1（要不要做第三条腿）**：即使做了，也不解决这一例。她在第一次失败后就停了；
  再准的腿也得先有人**要**它的结果。腿是给「系统替她判断」用的，不是给「她自己查」用的。
- **问题 3（未接住的对话作第二因子）**：**方向记反了**。复核出站表：小伊最后一句在 07-26，
  小腻 **08-08 还伸过手**（「你最近怎么样」）。真实状态是**她伸手了对方没接**，
  不是「对方说了她没回」。两种状态的产品含义完全不同 —— 后者她能了结，前者她只能等。
- **新问题（本附录提出）**：要改的是哪一层 ——
  ① 她对「查不到」的归因；② 她被打断的密度（95 秒 6 条，全是在确认她错了）；
  ③ 她把「查记忆」等同于「grep 宫殿」（`qq-usage` 在她概念里是「手机」不是「记忆」）。
  **三者互不替代**：归因治好了她仍然会被每 10 秒一条的流打断；
  打断治好了她仍然只会 grep 宫殿。
